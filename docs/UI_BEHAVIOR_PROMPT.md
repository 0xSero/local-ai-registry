# Registry browser behavior prompt

Build a local-first application for exploring and running the Local AI Registry. Use `registry/index.json` as the initial document and progressively fetch referenced records only as the user asks for more detail. Do not load every JSON file at startup. The application must work against a local filesystem checkout and against the same tree hosted as static HTTP.

The first useful state should identify the local machine when hardware detection is available, match it to one or more registry hardware IDs, and show compatible models. If automatic detection is unavailable or ambiguous, let the user choose a hardware profile without blocking the rest of the application. Make the detected facts, the matched registry record, and any assumptions separately inspectable.

List hardware, models, model instances, recipes, and speed sweeps. Hardware entries should expose vendor, accelerator name, memory capacity and type, backend, aliases, and the Mac product families associated with an Apple chip. Model entries should expose their canonical family and source. Model-instance entries should expose the exact repository, revision, quantization, size when known, and whether that artifact is pinned. Recipe entries should connect the selected artifact, hardware, engine, launch contract, capabilities, status, and evidence without duplicating those records.

Default the main model list to the detected or selected hardware. Let users change the hardware count when a recipe supports multiple identical GPUs, then recalculate compatibility. Keep candidates visible but distinguish them from validated recipes in every list and detail state. A candidate can show measured evidence and source notes, but it cannot claim that the recipe is reproducible or runnable.

Provide one search that works across hardware IDs and aliases, accelerator names, Apple chip names and product families, model names and families, Hugging Face repositories, quantization names, engines, recipe IDs, statuses, capabilities, and evidence fields. Search should update as the user types and preserve active filters. Filters should include vendor, memory capacity, accelerator backend, model family, engine, status, launch kind, capability, evidence availability, context size, concurrency, and measured decode speed. Every filter must be removable independently and there must be a clear way to reset the search state.

Let the user sort compatible recipes by model name, memory requirement, context, single-stream decode speed, aggregate speed, prefill speed, time to first token, and evidence date. Missing measurements must remain visibly unknown rather than becoming zero. When several sweeps exist, show which row is being used for sorting and let the user inspect the full set of concurrency and context measurements.

Every record detail should provide Copy actions for its ID, source URL, raw JSON, static API path, model repository, pinned revision, and any validated launch command that can be safely constructed. A copied launch command must be generated from tokenized fields in the launch contract, never from a candidate note or source command snippet. Report copy success and keep the copied value inspectable.

Offer Run only for a recipe whose status is `validated`, whose model revision is pinned, whose runtime contract is pinned, and whose hardware requirements fit the detected machine. Before running, show the exact command, image or native runtime pin, model download, mount paths, port, environment, device count, and estimated disk requirement. Let the user change only fields the contract marks configurable. Require explicit confirmation before downloading weights, pulling an image, creating files, or starting a service.

Running should execute locally. Show each phase separately: validating the contract, checking disk and runtime prerequisites, locating or downloading weights, pulling or verifying the runtime, starting the process, waiting for the endpoint, fetching the served model list, sending a real completion request, and measuring a short smoke result. A listening port or running container is not enough to mark success. The final healthy state requires a successful completion in the model's supported API dialect.

While a model is running, expose endpoint address, served model name, uptime, process or container identity, hardware utilization when available, logs, stop, restart, copy endpoint, and copy client configuration. Keep localhost as the default. If Tailscale sharing is supported, make it a separate deliberate action that explains what address becomes reachable; never publish or expose a port automatically.

If a recipe is a candidate, replace Run with an explanation of what is missing: model revision, runtime pin, translated arguments, compatible hardware validation, completion proof, or speed acceptance. Link back to its source evidence and make the candidate JSON copyable so it can be curated into a proper recipe.

Support direct links to any hardware, model, model instance, recipe, or speed sweep ID. A direct link should load only that record and then resolve its immediate references. Back and forward navigation must preserve search text, filters, sort order, selected hardware, and expanded evidence.

Handle offline and partial-data states. Cache the last valid index and records for read-only browsing. If a refresh fails, preserve the previous cache and report the failing URL and time. If a reference is missing, show the broken field and ID without hiding the rest of the record. Never replace an existing valid cache with an incomplete response.

Expose the registry version, source base URL or local path, record counts, last successful refresh, and validation status. Provide a raw-data mode that shows the exact JSON for the current record and a reference trace that explains each fetch from `recipe` to `model-instance`, `model`, `hardware`, and `speed-sweeps`.

The application succeeds when a new user can open it, see what their machine can run, search the broader registry, compare the evidence, copy useful identifiers and configuration, and start one validated local model without editing configuration files or understanding the registry internals.
